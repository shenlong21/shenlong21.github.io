A company-wide platform on .NET Core and React, and a WHO project before it.

Pramaan keeps 320 machines in line with security policy

Pramaan is Argusoft’s internal Security Configuration Assessment and Mobile Device Management platform. It keeps the company’s machines compliant with CIS benchmarks, and lets the SecOps team manage software installs, watch for compliance drift and act on incidents. It is used by 350+ employees.

Sachin designed its original architecture: a CQRS/MediatR backend on .NET Core, a React 18 and TypeScript frontend, and real-time updates over SignalR. He later moved to other work, and has since come back to build on it.

His drift-tracking engine, built on EF Core, shows engineers compliance runs across all 320 machines as they happen, with a terminal-style live view built on SignalR and xterm.js. It replaced manual CIS-score audits.

Why not event sourcing?

For drift tracking, he chose periodic EF Core state diffing over event sourcing. Compliance runs on a schedule, so event-level history wasn’t needed. Idempotent, scheduled automation bundles were cheaper to run and still guaranteed consistent machine state.

The simpler pattern was the right one.

Investigations

A query EF Core couldn’t translate

An in-memory compatibility check inside an EF Core .Where() couldn’t be translated to SQL and crashed at runtime. He materialized the query before filtering, and fixed a second call site with the same failure, not just the one that was reported.

Failures reported as successes

The frontend’s HTTP middleware swallowed error codes, so failed bundle assignments and imports showed as successful, and users were acting on them. Explicit status-code checks fixed it.

Two editors, one counter

A shared code editor’s line numbers, drawn with CSS counters, broke when two editors appeared on one page. Scoping the counter per instance fixed it, and also turned on Bash and PowerShell highlighting, which had never worked.

AI & LLMs

Working LLM features, built with AI tools, and open about it.

RAG Document Q&A answers only from your documents

ASP.NET Core and .NET 8, the OpenAI SDK, EF Core with SQLite

Upload documents into a project, then ask questions or ask for a summary. An LLM writes the answer, but only from what’s in the documents. If they don’t contain the answer, it says so instead of guessing.

  1. Documents are split into ~500-token passages at sentence boundaries, with a 50-token overlap so no idea is lost at a boundary.
  2. Each passage is embedded as a vector and stored in SQLite, or in memory for tests.
  3. A question is embedded the same way and compared to every passage by cosine similarity.
  4. The best passages are packed into the prompt, capped at 3,000 tokens so retrieval can’t overflow the model’s context.
  5. If nothing scores above 0.5 similarity, it answers “I couldn’t find relevant information” without calling the LLM at all.

Deliberate trade-offs. A linear scan instead of a vector database, because a few documents per project don’t need one; the IVectorStore interface lets an ANN index slot in later without touching callers. Thin wrappers over the OpenAI SDK with a configurable base URL let the same code run against OpenAI, Google Gemini and a local Ollama model, and all three are verified end to end.

Honest limits. It hasn’t been load-tested or run on a large corpus, retrieval is O(n) per query, and the SDK wrapper is covered by a smoke test rather than unit tests.

How it was built. With heavy use of Claude Code. He can explain and defend every decision above.

Work in progress

Fight Club: a 3D fighting game with netcode that has to agree with itself

C# and .NET on the server, TypeScript and Babylon.js in the browser

A browser fighting game in the spirit of Bloody Roar 2. The combat simulation is deterministic fixed-point code, ported line for line from C# on the server to TypeScript on the client, and proven bit-identical by comparing golden-replay hashes.

The client predicts its own inputs on a 60 Hz fixed timestep and corrects mispredictions with hard resyncs from server state rather than smoothing them over, because smoothing can hide real bugs. Game state travels in a hand-rolled binary protocol. The browser client uses WebSockets today; the server also speaks WebTransport.

Opinion

Four habits that keep showing up in his work.

A failure you can see beats a success that isn’t one.

Fail loudly

Offline agents now fail visibly instead of reporting success. Failed imports no longer show a success message. The password-expiry policy got a follow-up when it started locking people out. Many of his fixes turn a silent failure into a visible one.

Pick the simpler pattern when it fits

State diffing instead of event sourcing for drift tracking. A linear scan instead of a vector database for RAG, behind an interface so it can grow later. The sophisticated option is only right when the problem needs it.

Read the rulebook critically

A CIS rule that is secure by the book was breaking the company’s own installer. Compliance content is a starting point, not something to apply blindly.

Say how it was built

AI tools are part of how he works, and he discloses where they helped. What matters is understanding why the code is built the way it is and being able to defend it.
